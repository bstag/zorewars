# Captured pMARS preprocessor probes

These original Redcode programs are independent test inputs: 81 from the clean-room handoff, and probes named `fuzz-*` added afterwards for behaviour found by differential fuzzing (`scripts/fuzz-pmars.js`; their manifest entries have `"origin": "differential-fuzzer"`, and `scripts/capture-pmars-probes.js` captures them the same way). Expected stdout, stderr and exit codes are captured by running the pMARS 0.9.5 reference, with the capture date recorded in the manifest. No expected listing is calculated by ZoreWars or hand-authored. The manifest summary is refreshed by capture and checked against the corpus in tests.

See `../../docs/clean-room/pmars-preprocessor-behaviour.md` for the behavioural specification, source-review boundary, reference provenance, test conditions, case explanations and untested areas.

`manifest.json` is the corpus index. Run each case's `args` against the reference executable with this directory as the working directory. For example: `pmars-reference.exe -A equ-text.red`, or `pmars-reference.exe -A -8 88-for-equ.red`. Compare each output stream separately and check the exit code. All cases have a five-second reference-process timeout during capture; none timed out. File hashes protect the exact input and captured output bytes.

Most cases contain assembly-only output. Capture metadata headers with `node scripts/capture-pmars-probes.js --pmars path/to/pmars --metadata fuzz-after-end-metadata.red`: this runs one cycle with `-r 1 -c 1` to expose the name. Tests compare the header name and assembly, not the battle score. Subsequent captures preserve the case's recorded arguments. Successful reference exit is 0; rejection is 3. Warnings can accompany success. Some valid cases deliberately lack an assertion or instructions, or exercise surprising error recovery. Their names describe the construct, not an assumption that it must be accepted.

`fuzz-reference-access-violation` captures a reference process crash, with outcome `crash`. It is evidence for the process classifier, not an expected rejection by ZoreWars. Conformance tests exclude process failures and separately verify outcomes, summary totals and all input/output hashes. Capture records the executable hash on new entries. The differential fuzzer also saves crash/timeout/launch-error inputs and results separately from assembler mismatches.

Raw text outputs use the reference's CRLF. For implementation tests that compare assembled instructions rather than rendering, parse the listing and normalize fields modulo the configured core size; preserve origin and accept/reject separately. Do not require ZoreWars to use pMARS's process exit code or exact error wording unless that is a deliberate compatibility requirement.

No reference source, executable, or copied implementation is included. `scripts/capture-pmars-probes.js` is an implementation-side capture runner; `test/pmars-clean-room.test.js` consumes the manifest without reading reference source. This directory is outside `test/fixtures` because the existing comparison tool treats every direct child of that directory as a warrior file.

For comparable multi-seed fuzz runs, copy the `.red` inputs to a separate directory and pass it with `scripts/fuzz-pmars.js --corpus path/to/snapshot`. Each run writes `summary.json` with the reference executable hash, ordered corpus file hashes, seed and result counts. Keep that snapshot unchanged while adding newly captured regressions to this directory. This makes the verification pass generate the same inputs as discovery.

The 26 October campaign is recorded in `campaigns/2026-10-26.json`: four seeds, 3,000 programs per seed, followed by an identical verification pass. Discovery found 18 reports (17 unique minimized inputs). After fixes, verification found zero mismatches: 3,410 programs assembled identically and 7,502 were rejected by both. The remaining 1,025 empty programs, 53 reference crashes and 10 timeouts were excluded and counted separately. Seventeen captured reproducers plus seven controls bring the corpus to 156 cases. Every stored capture was replayed byte for byte against the reference; the full test suite passed (80 passed, one skipped).

The configured extension is recorded in `campaigns/2026-10-26-configurations.json`: ICWS'88 and '94, cores 80/97/800/8000/55440, seeds 1 and 42, 1,000 programs per combination (20,000 discovery inputs and the same 20,000 verification inputs). Each run records exact reference arguments and settings. Fifteen confirmed disagreements exposed two EQU/counter binding errors; four other reports were contradictory pMARS results, with fatal diagnostics despite exit 0. After the fixes and classifier correction, verification reported zero mismatches. Fifty-one new captures cover the reproducers, constants, wrapping, origins, dialect restrictions, length limits and explicit P-space sizes, bringing the corpus to 207 cases.

All 202 captures with reference language verdicts replay byte for byte. Five reference-failure captures are excluded from conformance. One inconsistent listing (`fuzz-config-94-80-1-002`) varies between executions; its captured hashes preserve evidence of that run, while live validation checks its `inconsistent` classification rather than requiring identical damaged output.

To capture configured probes, pass the fuzz summary's `referenceArgs` array via `--args`, for example `node scripts/capture-pmars-probes.js --pmars path/to/pmars --args '["-A","-8","-s","80","-l","5","-p","80","-c","800"]' probe.red`. The regression runner derives each case's settings and normalization modulus from its recorded arguments. Capture preserves these arguments on subsequent runs.
